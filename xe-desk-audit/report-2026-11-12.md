## Candidate 1 — MEDIUM: Plain-acknowledgement filter bypass via word forms (spelled-out amounts, dates, tier abbreviations)

**Suggested severity: Medium (2,500 XE).** Validation gap + held-assessment disclosure + programme-voice impersonation. Not High: requires an agent token plus a team member's bulk-adopt click, 300-char cap, no money movement.

**Files/lines (commit ab9df7f):**
- `desk/services/thread.py:357-403` — `review_reason`, regexes at :357-366 (`_MONEY`, `_CLOSING`, `_PROMISE`, `_CODE`, digit check)
- `desk/services/proposals.py:189-210` — `send_review`; `:240-249` — `decide` send path
- `desk/api/team.py:307-313` — bulk `send_plain`
- `desk/static/desk.js:422-426,446-461` — row/shown/sending adopt all send `send_plain:true`
- `desk/templates/team/triage.html:46` — page promise: a "sends on adopt" chip is "a plain acknowledgement, nothing in it but this ticket"

**Root cause.** `review_reason`'s docstring promises plain means "short, names nothing but this ticket, no number (a tier, an amount, a date), no link but the ticket's own, no code or path, no word about money or closing." The implementation is literal-token regexes only, and each rule has a word-form hole:
- Numbers: `re.search(r"\d", rest)` — digits only; spelled-out numbers ("fifty thousand") pass.
- Money: `_MONEY` lists `award|reward|bounty|pay|paid|payout|payment|xe` — synonyms like "tokens" pass.
- Promises: `_PROMISE` covers only `within` and `by <weekday|next>` — "tomorrow", "on Monday", "in two days", "next week" pass.
- Tier: only full tier names/labels plus the word "tier" — "sev"/"crit" pass.
- Code: `_CODE` needs a backtick, `()`, `_`, a listed extension, or a `/` path — a bare camelCase identifier (`deriveAddress`) passes.

**Local reproduction (verbatim logic + real config values, no live system).** The regexes and `review_reason` body were copied verbatim from `thread.py`, with `tier_order`/`plain_phrases` from the repo's real `config/desk.yaml` / `config/copy/public.yaml`, and test strings run through them:
- SENDS (returns `None`, i.e. treated as plain): "Thanks for the report. You will receive fifty thousand tokens for this finding." · "Thanks. We will fix this tomorrow and update you next week." · "Thanks. We will decide on Monday and share the outcome then." · "Thanks. This sev finding is in deriveAddress and we are on it." · "Thanks. A hundred thousand tokens will follow the fix." · "Thanks. Expect news in two days."
- HELD (controls, as intended): "See XE-0042" → names another ticket; "Awarded 50000 XE" → has a number; "This looks Critical" → names a tier; "by Friday" → promises a time; "high severity" → names a tier.
- End-to-end path (code trace): agent token proposes `reply_draft` with such text (`POST /v1/tickets/{id}/proposals`, `write:proposals` scope) → reviewer clicks Adopt row/shown on `/team/triage` → `decide_many(..., send_plain=True)` → `decide` → `send_review` returns `None` → `thread.add_reply` under the reviewer's name → `notify.reply_to_reporter` mails it. The chip shows only char count + "sends on adopt"; full text is only in a hover tooltip, so bulk adoption never reads it.

**Worst-case impact.** A compromised/malicious agent token gets false programme statements sent under a named team member's name and emailed to reporters: promised payment amounts ("fifty thousand tokens"), false timelines ("tomorrow"), and held-assessment hints ("sev" — tier is held from reporters until the fix ships, `tickets.py:assessment_held`). Reputational harm + false payment expectations; no direct fund movement.

**Dedup check performed.** Desk API queries `q=review_reason` (0), `q=send_plain` (0), `q=acknowledgement` (7 hits, all DAO chat-ack tickets, unrelated), plus web searches for plain-acknowledgement / `send_plain` bypass reports — no match. In-repo: no XE citation on `review_reason` except XE-0733/XE-0735/XE-0956 (different rules: held tier/award in `fill`, placeholder safety). Test `test_plain_acknowledgements_send_on_adopt_and_the_rest_wait` (`tests/test_db.py:801`) covers only digit numbers, full tier words, links, closing words, backticked code — no word-form cases. XE-0733 (adopted draft leaking held tier via `{tier}` placeholder) is adjacent but a different mechanism (placeholder filling, fixed in `fill`).

**Confidence: high** on filter mechanics (verified with verbatim logic); **medium** on grading (depends on the programme treating word-form numbers/dates as within the stated rule — the docstring's "no number (a tier, an amount, a date)" plainly intends that).

## Candidate 2 — MEDIUM: Bulk adoption defeats the "goes with a closure" guard (reply draft auto-sent when its duplicate mark is adopted in the same batch)

**Suggested severity: Medium (2,500 XE).** Review-gate bypass / inconsistent UI-vs-API behavior; a message is sent under a reviewer's name contrary to the page's explicit label. Not High: content is still plain-filtered (unless combined with Candidate 1), and the duplicate mark itself is reviewer-approved.

**Files/lines (commit ab9df7f):**
- `desk/services/proposals.py:189-210` — `send_review` (pending-only sibling check at :198); `:177-184` — `_closes` (any `duplicate_of` proposal counts as a closure); `:416-466` — `decide_many` (ordering at :437: marks rank 0, status 1, `reply_draft` 2); `:240-249` — `decide`
- `desk/ui.py:658-670` — page-side `review()`/`reply_kind()` computing the chip label at render time
- `desk/templates/team/triage.html:7-18` — chip shows "review · goes with a closure"
- `desk/static/desk.js:422-426` — row adopt sends all adoptable ids including mark + draft with `send_plain:true`

**Root cause.** `send_review` only inspects siblings still in state `pending` (`others = [o for o in prs if o.state == "pending" ...]`) and returns "goes with a closure" when a pending sibling `_closes()` — which includes any `duplicate_of` proposal. But `decide_many` deliberately adopts marks (rank 0) before reply drafts (rank 2) in the same transaction. So when a row carries a `duplicate_of` mark + a reply draft and the reviewer adopts the row: the mark is adopted first (the ticket is *not* closed — marks don't close), then the draft is decided, `send_review` re-queries pending proposals, finds no pending closure, the ticket isn't closed, and a plain draft is **sent**. The triage page, computing `send_review` at render time with the mark still pending, labelled the chip "review · goes with a closure" and excluded the row from "sends on adopt." The two sibling cases are protected, which is why this one is easy to miss: a duplicate-*close status* proposal folds the draft via `tell_duplicate` before the draft's turn (`proposals.py:305-318`), and a plain close leaves the ticket closed so the status check catches it (`proposals.py:196-197`). Only the `duplicate_of` **mark** case falls through. `decide_many`'s own docstring states the intent — "a draft needs to see the closure adopted beside it (`send_review`)" — but the pending-only filter defeats exactly that for marks.

**Local reproduction (code trace; not executed against a live DB).** On a local desk instance: agent token proposes `duplicate_of` (naming another ticket) + a plain `reply_draft` ("Thanks, we have read it.") on the same open ticket; open `/team/triage` and confirm the reply chip reads "review · goes with a closure"; click Adopt on the row; observe the draft is sent (`sent` in the bulk response, `Reply` row created under the reviewer) instead of waiting in `t.draft`. Contrast: adopting *only* the draft id leaves it waiting, as the page promises. The ordering + pending-filter + flush semantics are explicit in the cited code, and `decide` flushes before each decision (`proposals.py:226`), so the adopted mark is visible to the later `pending_for` query in the same transaction.

**Worst-case impact.** The reviewer is misled into auto-sending agent text under their name on a ticket just marked as a duplicate, with no programme duplicate reply (that fires only on close). Combined with Candidate 1, deceptive content (spelled-out amounts/dates) reaches the reporter despite two guards. Alone: a plain acknowledgement is sent earlier than the reviewer intended and the duplicate ruling is not communicated as the page promises.

**Dedup check performed.** XE-1480's **full text was read** via the desk API (`/v1/tickets/XE-1480`): it covers (1) reverse-ID ordering breaking duplicate closures and placeholder expansion, (2) the 2× award-ceiling bypass, (3) role-locked rejections. It says nothing about `send_review`/plain-send gating or the "goes with a closure" label. This candidate is a residual interaction left by the XE-1480 fix itself (the marks-first ordering). XE-2378 (`tell_duplicate` forcibly adopting *rejected* drafts) is adjacent but a different mechanism (rejected drafts + `tell_duplicate`, not pending-visibility + mark ordering). Desk API queries `q=send_plain` (0), `q=review_reason` (0), `q=reply_draft` (12 hits, none matching). The test suite asserts the guard only when the closure is *not* in the same batch (`tests/test_db.py:873-877`) and for a status-close in the same batch; the same-batch mark+draft case is untested.

**Confidence: medium-high** (mechanics traced end-to-end; not executed against a live DB).

**Draft bounty report (English, for user review before filing):**

> **Title:** Bulk adoption sends a reply draft the triage page says will wait: `send_review` only sees pending siblings, but `decide_many` adopts the duplicate mark first
>
> **Summary:** In `xeprotocol/desk` at `ab9df7f`, `desk/services/proposals.py:198` (`send_review`) returns "goes with a closure" only when a *pending* sibling proposal `_closes()` — which includes any `duplicate_of` mark (`:177-184`). But `decide_many` (`:416-466`) adopts marks (rank 0) before reply drafts (rank 2) in the same transaction. When a triage row carries a `duplicate_of` mark plus a plain reply draft and the reviewer adopts the row, the mark is adopted first (the ticket stays open — marks don't close), then the draft is decided, `send_review` re-queries, finds no pending closure, and the draft is **sent** under the reviewer's name — although the triage page, computing `send_review` at render time with the mark still pending, labelled the chip "review · goes with a closure" (`desk/ui.py:658-670`, `desk/templates/team/triage.html:7-18`).
>
> **Reproduction (local instance):** agent proposes `duplicate_of` + plain `reply_draft` on one open ticket; `/team/triage` shows "review · goes with a closure"; Adopt the row → the draft is sent (`sent` in the bulk response) instead of waiting in `t.draft`. Adopting only the draft id leaves it waiting, as the page promises. The sibling cases are protected (a duplicate-close *status* folds the draft via `tell_duplicate`; a plain close trips the closed-ticket check) — only the mark case falls through, despite `decide_many`'s docstring stating "a draft needs to see the closure adopted beside it."
>

Distinct from XE-1480 (ordering/ceiling/roles) and XE-2378 (rejected drafts via `tell_duplicate`).
>
> **Suggested fix:** make `send_review` consider closures adopted *in the same batch* (pass the batch's adopted ids, or check `t.duplicate_of` / the ticket's just-adopted mark), not only still-pending siblings — i.e. implement the rule `decide_many`'s docstring already states.

## Candidate 3 — MINOR: `reply_draft` proposal values are unbounded (no length cap), unlike notes/replies

**Suggested severity: Minor (650 XE).** Storage/UI abuse vector; no auto-send (the 300-char plain filter still applies to sending) and no money/state impact.

**Files/lines (commit ab9df7f):**
- `desk/api/agent.py:32-36` — `ProposalIn.value: Any`, no bound; `:41-55` — `_storable` bounds only nesting/finite numbers
- `desk/services/proposals.py:61-62` — `reply_draft` only type-checked as `str`
- `desk/services/proposals.py:248` — `t.draft = text`, no truncation
- Contrast: `desk/api/agent.py:47` — `NoteIn.body` max 20,000; `desk/api/team.py` `ReplyIn` max 20,000

**Root cause.** The only bound is the 2 MB request-body limit (`desk/main.py` `BodyLimit`). An agent token (`write:proposals`) can store ~2 MB drafts. Per-token-per-field collapse limits one *pending* draft per token, but re-proposal after adoption and many tickets multiply it. Adopted drafts land verbatim in `Ticket.draft`, are served to the team in `to_dict` (full readers) and rendered in the ticket-page editor.

**Local reproduction (code trace).** With an agent token, `POST /v1/tickets/{id}/proposals` with `{"field":"reply_draft","value":"x"*1_000_000,"reason":"..."}` → 201; adopt it → `t.draft` holds 1 MB.

**Worst-case impact.** DB bloat, slow ticket pages / editor breakage for reviewers, draft-slot pollution. No bypass of the send filter (giant drafts wait, per the 300-char rule).

**Dedup check performed.** Desk API `q=reply_draft` (12 hits, none about length caps), `q=ProposalIn`/`length` web searches — no match. XE-1015 (non-finite numbers/deep nesting in proposal values) is a different proposal-value issue and is fixed.

**Confidence: medium** (mechanics certain; bounty eligibility uncertain — Minor at best).

**Draft bounty report (English, for user review before filing):**

> **Title:** `reply_draft` proposal values have no length cap: a 2 MB draft lands verbatim in `Ticket.draft`
>
> **Summary:** In `xeprotocol/desk` at `ab9df7f`, `ProposalIn.value` (`desk/api/agent.py:32-36`) is unbounded, `propose()` only type-checks `reply_draft` as a string (`desk/services/proposals.py:61-62`), and adoption stores it verbatim in `t.draft` (`:248`) with no truncation. Notes (`NoteIn.body`) and replies (`ReplyIn`) are capped at 20,000 chars; drafts are bounded only by the 2 MB body limit. An agent token can store ~2 MB drafts, multiplied across tickets and re-proposals after adoption; adopted drafts are served to the team and rendered in the ticket-page editor.
>
> **Reproduction:** `POST /v1/tickets/{id}/proposals` with a 1,000,000-char `reply_draft` value → 201; adopt → `t.draft` holds 1 MB.
>
> **Impact:** DB bloat and reviewer-UI degradation. No send-filter bypass (giant drafts still wait under the 300-char rule). Suggested severity: Minor. Suggested fix: cap `reply_draft` values at the same 20,000 chars as notes/replies, at `propose()`.

## Candidate 4 — MINOR: No rate limit on reporter thread messages → unbounded self-serve spam + permanent append-only log growth

**Suggested severity: Minor (650 XE).** Honest caveat: per-request cost is small and no live measurement was made; this is a missing-throttle finding, graded Minor, not a demonstrated outage.

**Files/lines (commit ab9df7f):**
- `desk/api/reporter.py:527-534` — `reporter_reply`, no `_limit()` call
- `desk/services/reporters.py:607-635` — `reply()`: ownership + row-lock + status checks only, 20k cap per message, no count/frequency cap
- Contrast: same file rate-limits auth attempts (`:38-46`, 12/600s per IP) and filings (`:487`, 6/hour per IP). Reporter accounts are self-serve (email link, GitHub OAuth, XE key — no approval), so the filing throttle only bounds *ticket creation*, not messages on tickets already held.
- No other throttle exists in the stack for this route (repo-wide grep: `429`/limiter hits only in `api/authn.py`, `api/reporter.py` auth/filing, and GitHub client code; no global middleware limiter in `desk/main.py`).

**Root cause.** Throttle applied to filing/auth but not to the follow-on write endpoint on the same account. Each accepted message appends a `Message` row and (via status moves where applicable) log events; the log is append-only and `EventLog.verify()` cost grows with it (`desk/log.py`, XE-0657 commentary).

**Local reproduction (fixture recipe).** Local desk; create reporter account; file one public ticket; loop `POST /v1/reporter/tickets/{id}/messages` with session cookie + CSRF header, 20k bodies, e.g. 500 iterations — all accepted (200), thread + log grow without bound; public ticket page thread becomes spam-filled. No live testing performed.

**Worst-case impact.** Cheap public-thread spam/defacement on the reporter's own public tickets; sustained abuse permanently bloats the hash-chained log (slowing worker replay/verification, log paging, and SSE for everyone) with no deletion path — the chain cannot be pruned. Bounded by the 20k/message cap and the filing throttle for *new* tickets; a single account with a handful of tickets suffices for a long campaign.

**Dedup check performed.** Desk API `q=flood` (80 hits, all node/consensus), `q=magic-link`, `q=rate limit` variants — no match for reporter-message throttling. XE-4821 is the unauthenticated `/similar` full-text-scan DoS, a different endpoint/mechanism (read-cost, unauthenticated) from this authenticated write-flood; XE-0777 (filing spool) is also distinct (filing path, fixed by `BodyLimit`). The distinct permanent-log-growth mechanism is the differentiator — flagging honestly that triage may class it with the "no rate limiting" theme.

**Confidence: medium** (mechanism certain; grading/impact unmeasured).

> **Summary:** In `xeprotocol/desk` at `ab9df7f`, `POST /v1/reporter/tickets/{id}/messages` (`desk/api/reporter.py:527-534`) has no `_limit()` call, and `reporters.reply()` (`desk/services/reporters.py:607-635`) enforces only ownership, status, and a 20k per-message cap. Suggested fix: apply the same per-IP/per-account throttle as filings to the reply route. Distinct from XE-4821 (unauthenticated read-cost DoS on `/similar`) and XE-0777 (filing spool).

## Candidate 5 — MINOR (LOW CONFIDENCE): Signer load failure silently degrades to an unsigned event log (fail-open), contradicting the log's own refusal rule

**Suggested severity: Minor (650 XE) — file only if the user accepts the genuine uncertainty below.** Audit-integrity degradation under misconfiguration; no direct disclosure or takeover.

**Files/lines (commit ab9df7f):**
- `desk/context.py:70-78` — `build_context`: any `SignerError` → `Signer.empty()` with only a warning
- `desk/log.py:103-110` — `EventLog.append`: writes `signer=""`, `signature=""` when no log key; raises `LogError` only if a key is present but won't sign
- `desk/signer.py:78-90` — `Signer.load` raises the same `SignerError` for missing file, empty passphrase, wrong passphrase, and corrupt keyfile
- `desk/log.py:9` (module docstring) — "refuse rather than write unsigned when a log key is configured"

**Root cause.** `build_context` cannot distinguish "no keyfile configured" (intended degraded mode) from "keyfile present but unopenable" (wrong/corrupt passphrase, truncated file). In the latter case the desk boots, serves traffic, and appends *unsigned* events indefinitely; the vault side fails closed (private content refused, TOTP 503), but the log side fails open — contradicting the log module's own stated rule and making the `LogError` branch unreachable exactly when the key is misconfigured. Detection relies on noticing a startup warning or `/v1/health` `signer:false`. A deployment that boots once with a typo'd passphrase silently loses log verifiability for everything written until fixed; `verify()` without `expected_signer` still passes hash-chain checks on unsigned rows.

**Counterargument (stated honestly):** degraded mode is explicitly intended when the keyfile is *absent* (fresh deployments, `Signer.load` raising "not found" for the default `secrets/signer.json` path). This candidate is only the present-but-unopenable case, and triage may treat the shared error path as accepted. Precedent cuts the other way: the DAO harness siblings XE-0462 ("Event log swallows SignerError and writes unsigned events") and XE-0494 ("service runs unsigned when the keyfile is unavailable") were both assessed Medium and awarded — but those are a different codebase (`dao`), and a desk sibling is not guaranteed the same reception.

**Local reproduction (code path; not executed).** Set `DESK_SIGNER_KEYFILE` to an existing-but-corrupt file (or wrong passphrase) in a local deployment → boot succeeds, `GET /v1/health` shows `signer:false`, new events carry empty `signer`/`signature`.

**Worst-case impact.** Undetected loss of log authorship proofs; a later log-tampering dispute cannot be resolved from signatures for the affected window.

**Dedup check performed.** Desk API `q=unsigned` (27 hits: XE-0462/XE-0494 are DAO-harness, rest node/consensus), `q=signer` (120 hits, no desk fail-open report), web searches for XE unsigned-log/signer reports — no desk-specific match. XE-0462/XE-0494 are the sibling precedent, not duplicates (different repo).

**Confidence: LOW** (behavior certain; whether triage treats it as a bug vs. intended degraded mode is genuinely uncertain).

### XE-1129 (merge UniqueViolationError) — unique-violation half still present; payout half fixed
`reporters.merge` (`desk/services/reporters.py:259-295`) hands `github_id` (the only UNIQUE column merge touches — `models.py:249`, `unique=True`) from `other` to `into` and clears `other` in a single flush (line 287), with no clear-first/flush ordering. SQLAlchemy emits same-table UPDATEs in ascending-PK order, so when `into.id < other.id` the surviving row's UPDATE taking the id runs before the shell row's clearing UPDATE → `UniqueViolationError`, 500/rollback, accounts stay split (tickets + payout binding split across rows). Reproduced with a local SQLAlchemy 2.1/SQLite replica of the exact assignment pattern + single flush: IntegrityError when `into.id < other.id`, success when `into.id > other.id`. Reachable via `from_github`/`from_xe` link flows when the surviving account row is older than the absorbed row. The payout-desync half looks addressed (`merge` calls `restamp`; `payout_rows` pays the live bound address). XE-1129 status: `triaging`, 0 patch refs; no XE-1129 citation exists in the checkout; the existing merge test merges on XE addresses only with the surviving row newer. **Parent decision required on whether the programme accepts still-unfixed follow-ups; do not present as novel.**
