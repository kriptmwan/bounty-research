D1. 64-byte EIP-2098 signatures with yParity=1 REVERT on the 1271 path but
  validate on the 4337 path. TRACE (correct as a code fact): the inherited
  ERC-7739 base reads s := calldataload(signature.offset + 0x20) and reverts
  InvalidSignature() if s > n/2; for a 64-byte sig that word is `vs`, whose
  top bit set (yParity=1) makes vs >= 2^255 > n/2, so it always reverts;
  meanwhile Solady tryRecoverCalldata (ECDSA.sol L202-233) has an explicit
  64-byte branch deriving v from the vs top bit, so K1Validator.validateUserOp
  (L147-149) accepts the same signature. KILLED as a reportable finding:
  (a) the defective check lives in THIRD-PARTY erc7739-validator-base, not in
  any assigned file — bounty scope excludes third-party components (SCOPE §1,
  EXCLUSION_LIST §H.6; cf. EX-079); the K1 call site (L168-174) is the
  documented usage pattern, identical in the upstream sample validator;
  (b) no documented promise that the 1271 path accepts 64-byte encodings —
  all tests/tooling use 65-byte; (c) fail-closed (rejects, never accepts
  invalid); (d) trivial lossless workaround (re-encode as 65-byte r,s,v).
  Counter-evidence: poc ERC7739Validator.sol s-check block; SampleK1Validator
  identical shape; TestK1Validator.t.sol uses abi.encodePacked(r,s,v) only.
  No POC needed: the trace is statically complete; the verdict turns on scope
  and impact, not execution.
D2. Empty inner signature + magic hash returns 0x77390001 through the NORMAL
  isValidSignature path (20-byte validator prefix + empty remainder; detection
  branch at Nexus.sol L376-380 skipped since length != 0; K1 detection check
  fires on the empty remainder). KILLED: 0x77390001 (SUPPORTS_ERC7739_V1,
  Constants.sol L59) is distinct from ERC1271_MAGICVALUE 0x1626ba7e
  (Constants.sol L14); every in-repo consumer compares == ERC1271_MAGICVALUE
  (ModuleManager.sol L462 emergency, L525-527 enable mode); the detection
  return code is spec'd behaviour, and the same value is returned by the
  legitimate detection path — no consumer confusion, no bypass.
D3. K1 _erc1271CallerIsSafe adds `sender == msg.sender` (K1Validator.sol
  L248-253), a deviation from the upstream sample, skipping the nested
  EIP-712 workflow. KILLED: no new principal. Enable/emergency paths pass
  sender == account AND the digest is already account-bound via _hashTypedData
  (ModuleManager.sol L520, L539, domain verifyingContract = account); the
  isValidSignature self-call case requires owner-validated execution; direct
  calls to K1 key the owner lookup by msg.sender (K1Validator.sol L236-237
  getOwner(msg.sender)), so an attacker can only validate for their own key.
  Counter-evidence: ModuleManager.sol L520/L539; K1Validator.sol L236-237.
D4. Safe-sender set false positives / stale entries (EnumerableSet4337).
  KILLED: _contains returns positions[value][account] != 0
  (EnumerableSet4337.sol L335-337) — empty set returns false, no false
  positive; _removeAll (L48-56) captures length once and removes from the
  last index backwards, correctly clearing swap-and-pop state; _add/_remove
  (L280-333) maintain the position invariant. No spurious safe-caller.
D5. Permissionless direct calls to onInstall / transferOwnership /
  addSafeSender / removeSafeSender (K1Validator.sol L77/L100/L107/L112, all
  keyed by msg.sender) let an attacker set a victim account's owner or safe
  senders. KILLED: the key is msg.sender, so a direct caller affects only
  their own key; affecting an account's key requires the account itself to
  call (owner-validated execute) or, for 7702 accounts, the EOA itself (the
  owner key — no incremental privilege, H-B1 reasoning, EX-136).
  Counter-evidence: K1Validator.sol L80/L102/L108/L113 (msg.sender keys).
D6. Dual recovery (raw hash OR eth-signed-message hash, K1Validator.sol
